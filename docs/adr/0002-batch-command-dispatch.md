# Batch Command Dispatch — Asynchronous, Serialized, PTY-Streamed

Batch Command dispatches one multi-line script to a set of servers and streams each server's live interactive terminal output to a browser dialog, so an operator can watch per-server status and answer interactive prompts (e.g. typing "y" to an install confirmation) while a script runs. We chose an asynchronous, persisted design: `POST /api/batch-runs` returns immediately and a background runner executes the script on each target server concurrently; the frontend polls or reconnects rather than holding a long request open. A synchronous request-response alternative was rejected because it offers no per-server intermediate status, risks HTTP timeouts on long-running scripts, and cannot surface the "one server hung, the others finished" reality.

**Runs are serialized and non-historical.** Only one Batch Run exists at a time: a new dispatch replaces the previous Run, and a new dispatch is rejected with a conflict error while the current Run is still `running`. A manual cancel button terminates the PTY sessions on all target servers (each result ends `failed` with error `cancelled`). This "keep only the latest, no history" choice keeps the schema tiny and matches the operator's mental model ("I want to see the last thing I ran"), at the cost of no audit trail — a deliberate trade-off.

**PTY, not separate streams.** The script is written to a remote temp file and executed as `sh <file>` over a pseudo-terminal, leaving the process's stdin free for interactive input. This means stdout and stderr arrive merged into one terminal stream — SSH only exposes a single output channel once a PTY is in use. Separate stdout/stderr capture (no PTY) was considered and rejected: it breaks interactive prompts, because many programs behave differently or refuse input when they detect a non-TTY stdin. The merged stream is persisted as a single `output` column (truncated to a cap, marked `truncated`) on each per-server Run Result.

**Live phase over WebSocket, snapshot/final over REST.** The running phase uses a dedicated WebSocket endpoint so keystrokes and terminal output travel bidirectionally in near-real-time; REST is used only for the dialog's initial state and the post-run final results. This is consistent with the "Process data over REST, not WebSocket" precedent — on-demand data stays out of the 2-second metrics broadcast — while acknowledging that interactive typing cannot wait for a poll interval. The batch WebSocket is a separate endpoint from the metric hub; it does not touch the broadcast payload.

**Selection via the dialog's tri-state tree.** Group rows and server rows share the same checkbox control: checking a Group selects all its members, an individual server can be checked alone, and a Group renders indeterminate when partially selected. Selection lives only inside the dialog (never in the sidebar or dashboard), keeping the run-at-a-time model obvious and the busy sidebar rows uncluttered. Servers in a `reconnecting`/`failed` Connection State are still dispatchable — they run immediately to a `failed` Run Result carrying the connection error.
