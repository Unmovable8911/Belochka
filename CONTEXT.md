# CONTEXT.md — Belochka Domain Glossary

Belochka is a single-binary server monitor: it maintains persistent SSH connections to remote Linux hosts, collects system metrics, and streams them to a browser dashboard over WebSocket.

## Core Concepts

- **Server** — a remote Linux machine monitored by Belochka. Identified by a UUID, configured with host, port, SSH credentials (password or private key), and an optional host-key fingerprint for TOFU verification. Optionally belongs to a Group via `group_id` (nullable). `PUT /api/servers/{id}` accepts partial updates: omitted fields merge with existing values; only the fields present in the JSON body are changed. Persisted in SQLite.

- **Group** — a named root-level container that organizes Servers. Groups are flat (no nesting): a Server belongs to at most one Group (many-to-one) and Group names are globally unique. Deleting a Group leaves its member Servers ungrouped (`group_id` set to NULL). `PUT /api/groups/{id}` accepts a partial update: only `name` is optional; omitted fields keep existing values. The sidebar renders Groups as a flat expandable list; Servers with no Group (`group_id` NULL) render directly at the root of that list as siblings of the Groups (there are no virtual "All Servers"/"Ungrouped" nodes). HTML5 native drag-and-drop moves a Server into a Group (drop on a Group row) or out of a Group (drop on blank tree space); a right-click "Move to..." menu moves a Server to any Group or to "No group" (data transferred as JSON text via `dataTransfer`) — Groups themselves are not movable. Hovering a Group row reveals a compact delete quick-action; create/rename input happens in an in-app dialog, and deletion is confirmed in an in-app dialog (mirroring the server-delete flow) whose message states that the Group's member Servers become ungrouped. Blank space in the list area right-clicks to a root-level New Group menu. Clicking a Group filters the dashboard to that Group's direct members, with a breadcrumb for navigation. Group data is fetched once via `GET /api/groups` on load and re-fetched after mutations — it is not carried in the WebSocket broadcast. Persisted in SQLite.

- **Connection State** — each server's SSH connection is in one of three states: `connected` (healthy), `reconnecting` (lost, retrying with exponential backoff 1s→30s, max 5 retries), or `failed` (retries exhausted or non-retryable error). The dashboard shows this per-server and offers a manual reconnect button when failed.

- **Metrics** — raw readings from `/proc/stat`, `/proc/meminfo`, `df`, and `/proc/net/dev` collected in a single SSH exec per 2s cycle. Includes CPU (jiffy counters per core), memory (bytes), disk (per-partition usage), and network (interface byte counters). Process data is decoupled from this cycle — see Process below.

- **Snapshot** — a computed snapshot derived from two consecutive Metrics readings. CPU usage percentages and network rates (bytes/sec) require deltas; the first cycle produces a `partial` snapshot (no rates). Snapshots are the wire format broadcast to WebSocket clients.

- **Collector** — a per-server goroutine loop (2s interval) that executes the metrics command over SSH, parses output, computes deltas, and stores the latest Snapshot. After 3 consecutive failures it triggers SSH reconnection. After 5 consecutive failures (i.e., on the 6th and subsequent failures) it drops from WARN to DEBUG-level logging.

- **Pool** — the SSH connection manager. Maintains one persistent connection per server with keepalive pings (30s). Exposes `Execute`/`OpenSession`/`RunCommand` for consumers (monitor, terminal, cron, process, connection test). Owns reconnection logic.

- **Hub** — the WebSocket fan-out. Accepts browser connections (up to 10), caches the latest broadcast Snapshot, delivers it to new clients immediately, and fans out each 2s broadcast to all connected clients.

- **Broadcast** — assembles the JSON wire envelope (`{"type":"snapshot","data":...}`) from Pool connection states and Monitor snapshots, sent every 2s. Implemented by `BroadcastService` in `internal/app` — the assembly logic (`assemble`/`serverInfo`) lives in the same package, there is no separate broadcast package. It depends on narrow interfaces (`ServerLister`, `PoolStatusProvider`, `SnapshotProvider`, `hub.Broadcaster`) and is tested against the real Hub over real WebSocket connections (the hub_test pattern), with a zero-client fast path that skips assembly entirely.

- **Terminal Session** — a WebSocket-to-SSH bridge: browser opens a WebSocket, the backend opens an SSH session with PTY (xterm-256color), and binary frames flow bidirectionally. Resize events arrive as JSON text frames.

- **Cron Entry** — a single line in the remote server's crontab, parsed into schedule fields, command, and enabled/disabled status. Managed via `cron.Service` which reads the full crontab over SSH, modifies it in memory, and writes it back (base64-encoded for safe transport). The `#[disabled]` prefix convention marks disabled entries.

- **Process** — a running process on a remote server, fetched on-demand via `ps -eo pid,ppid,user,rss,%cpu,%mem,etime,args` through REST API (not WebSocket). Managed via `process.Service` which also supports killing processes (SIGTERM/SIGKILL). Critical processes (systemd, init, sshd) are protected from kill — the protection list is the single source of truth in `model.ProtectedCommands` / `model.IsProtectedCommand`. The `Process` struct carries two computed fields populated by the parser: `command_name` (executable name extracted from the full command path) and `protected` (whether the process matches the protected list). The frontend reads these directly from the API response rather than re-computing them client-side. The frontend renders a flat sortable table (no tree) with 3s auto-refresh polling via a toggle switch. Kill button uses a red `XCircle` icon, disabled when `protected` is true.

- **Batch Command** — the feature that dispatches one multi-line script to a set of Servers and streams each Server's live interactive terminal output to the browser. Entry point is a single button at the bottom of the sidebar opening the Batch Command dialog. The dialog composes a script and a server selection — a tree with tri-state checkboxes where checking a Group selects all its members and checking an individual Server row selects just that Server (the same checkbox control serves both) — then dispatches one Batch Run and shows per-Server status. Runs are serialized: a new dispatch is rejected while a Run is still `running` (see Batch Run).

- **Batch Run** — a single dispatch of one script to a set of Servers, with a per-Server Run Result for each. Persisted in SQLite; only the most recent Run is retained — a new dispatch replaces the previous Run (there is no run history). A Run has status `running` or `done`. The script is written to a remote temp file and executed as `sh <file>` over a PTY, so the process's stdin is left free for interactive input (e.g. answering "y" to an install prompt) and stdout+stderr arrive as one merged terminal stream. The running phase is streamed over a dedicated WebSocket; REST carries the pre-run snapshot and the post-run final state. Output streams to subscribers live as it is produced (not a burst at exit), so interactive prompts are visible while the process waits for input. The service's `Event` struct is itself the WebSocket wire format — its JSON tags are the protocol contract, and timestamps are fixed-width RFC 3339 UTC (via `EventTime`) because the frontend compares `finished_at` lexicographically; the handler marshals Events directly, there is no second wire struct. Streamed output is persisted at most once per flush interval (default 500ms, `WithFlushInterval` overrides it) so a burst of chunks does not write to the store per chunk; a failure to persist a finished Result's terminal state marks it `failed` with the persist error so the failure is visible to subscribers rather than logged away. Cancelling a Run terminates the PTY sessions on all target Servers. When the service starts, a Run left `running` by a previous process is finalized as `done` with its unfinished Results `failed` and error `interrupted by restart` — a stale Run must not block new dispatches (there is no crash-resume).

- **Run Result** — one Server's outcome within a Batch Run. Status is `pending`, `running`, `success`, or `failed` (a cancelled execution ends as `failed` with error `cancelled`). Carries `exit_code`, a single merged `output` stream — stdout and stderr are not separable over a PTY — which may be truncated (marked `truncated`), and `error`. Note that `failed` here is a Run Result status at a different layer from the `failed` Connection State (connection health vs execution outcome); the two are distinguished by context.

## Auth & Setup

- **First-run setup** — if no password hash exists in config, the frontend renders a two-step SetupPage wizard. Step 1: user selects a language (nine options, browser-detected language pre-selected). Step 2: user creates a password (min 6 chars) with a zxcvbn strength meter and confirm-password matching. `POST /api/setup` receives `{language, password, confirm_password}`, validates the language is one of `en/zh/fr/ru/de/es/pt/zh-TW/it`, then atomically persists both `Language` and bcrypt-hashed password to `config.json` and issues a session cookie.

- **Session** — a random token stored in an HTTP-only cookie, valid for 7 days (absolute expiry). Validated by chi middleware on all protected routes.

- **Rate limiting** — login failures are tracked per IP: 10 failures → 30-minute lockout. Successful login clears the counter.

- **Encryption at rest** — server passwords stored in SQLite are AES-GCM encrypted. The key comes from the `BELOCHKA_ENCRYPTION_KEY` env var (auto-generated if absent).

## Key Abstractions (Go interfaces)

- **Clock** (`internal/clock`) — abstracts `time.Now`, `time.NewTicker`, and context-aware `Sleep` for deterministic testing.
- **Executor** (`internal/ssh`) — executes a shell command on a remote server via SSH. Returns combined stdout+stderr; a non-zero exit code is returned as an error. Satisfied by Pool; consumed by monitor.Collector, cron.Service, and process.Service.
- **PTY Bridge** (`internal/pty`) — the single seam for SSH sessions with a pseudo-terminal: requests the PTY (24×80 xterm-256color by default), wires the stdin/stdout pipes, starts a remote process, and reports its exit status. `Opener.OpenInteractive` serves the terminal console; `Opener.OpenCommand` serves batch scripts (the consumer builds the command string, e.g. `sh <path>`). `Session.Wait()` returns an `ExitStatus{Known, Code}` in which the OpenSSH exit-status unreliability is resolved: a dropped exit-status message (gossh -1) surfaces as `Known: false` — "no exit status known", never a real exit code — and policy stays with the consumer (batchrun treats unknown as success without a recorded code). `NewOpener` takes a session opener function matching `*ssh.Pool.OpenSession`; consumed by terminal.Handler and batchrun.Service.
- **ServerProvider** (`internal/ssh`) — looks up a single server by ID via `GetByID`; consumed by Pool.Add(). Satisfied by Store. (Bulk listing for sync is provided by `ServerLister` in `internal/app`.)
- **ConfigStore** (`internal/config`) — canonical interface for application config: `Get`, `Update`, `Language`, `PasswordHash`, `BaseDir`. Single implementation (`*config.Store`); all consumers (auth, static handler, config API) depend on this interface rather than defining their own subsets.
- **Runner** (`internal/cron`) — executes a command and returns combined output plus the exit code separately (non-zero is not an error). Satisfied by Pool.
- **httpx** (`internal/httpx`) — HTTP helpers for JSON APIs: `WriteJSON`, `WriteError`, `DecodeJSON`, and the `ErrorBody` envelope type. Used by all handlers in `internal/api` and `internal/auth` so that JSON encoding, error formatting, and request decoding live in one place.
- **GroupStore** (`internal/api`) — defines Group persistence operations: `CreateGroup`, `GetGroupByID`, `ListGroups`, `UpdateGroup`, `DeleteGroup`, `GroupMemberCount`. Implemented by `*store.SQLiteStore`; consumed by `groupHandler`. Enforces global group-name uniqueness.
- **Broadcaster** (`internal/hub`) — the fan-out subset of Hub used by broadcast assembly: `SetSnapshot`, `BroadcastMsg`, `ClientCount`. Satisfied by `*hub.Hub`; consumed by `BroadcastService` in `internal/app`. The BroadcastService tests drive the real Hub over real WebSocket connections (the hub_test pattern) — a second adapter, so this is a real seam, not a hypothetical one.

## Architectural Decisions

- **SQLite over Postgres** — single-binary deployment with zero external dependencies. WAL mode for concurrent reads.
- **Persistent SSH connections over on-demand** — lower latency for 2s metric collection and instant terminal sessions.
- **Push metrics over poll** — WebSocket broadcast keeps every browser client in sync without polling `/api`.
- **SPA served from embedded FS** — the Go binary embeds the production Vite build; no separate web server.
- **Binary-relative paths** — config, data, and log paths resolve relative to the binary's directory (CWD fallback for `go run`).
- **syscall.Exec restart** — when port or data_dir is changed, `POST /api/restart` triggers `Application.Restart()` which gracefully shuts down all subsystems then calls `syscall.Exec` to replace the process image, preserving the PID (important for systemd/supervisor). The frontend closes the page after issuing the restart since the port may have changed.
- **Root-level Groups** — the `groups` table is a flat list (no `parent_id` self-reference); Group names are globally unique. At 5‑20 servers a flat model is sufficient: a Server holds a nullable `group_id` pointing to at most one Group, and deleting a Group ungroups its member Servers. There is no version-to-version migration — users re-add their Servers manually.
- **Groups outside WebSocket broadcast** — Group data is fetched once via `GET /api/groups` on page load and re-fetched after mutations (create, rename, delete, server move). The 2-second WebSocket broadcast carries only server connection states and metrics. This keeps the broadcast payload unchanged and means changing the Group filter only changes which server cards are shown, not what data is fetched.
- **Partial updates via PUT** — `PUT /api/servers/{id}` and `PUT /api/groups/{id}` merge the request body with the existing entity (cron entry updates at `PUT /api/servers/{id}/crons/{index}` are full replacement; `PATCH /api/config` uses pointer-based merge). For servers, the handler reads the existing row, decodes the body into a `map[string]json.RawMessage` to detect which keys were present, and only overwrites those fields before validating and saving. For groups, `Name` is decoded as `*string` (nil = keep existing, `&""` = rejected, `&"value"` = update). This allows drag-and-drop and the "Move to..." dialog to send only `{group_id}` without repeating the full entity.

- **Process data over REST, not WebSocket** — process lists are fetched on-demand via `GET /api/servers/{id}/processes` with 3s polling, not carried in the 2s WebSocket broadcast. This avoids wasting bandwidth on data the user isn't viewing (unlike CPU/memory/disk which are always visible on the dashboard). Process collection uses `ps -eo` per-request rather than `top` per-cycle; the old `top` section was removed from `CollectCommand()`, shrinking the metrics pipeline payload. The `process.Service` mirrors the `cron.Service` architecture: a single `Executor` interface satisfied by Pool, with a functional option (`WithProcessService`) gating the routes in the router.

## Frontend

- **SPA stack** — React 19 + TypeScript, Vite, Tailwind CSS v4, shadcn/ui (Radix primitives). Tests use vitest + jsdom + @testing-library/react. The `MonitorState` context (useReducer) drives the dashboard, fed primarily by a WebSocket listener that dispatches snapshot, connection, and server-removal updates into the reducer. The `add_server` action is dispatched optimistically from the Dashboard component (not from WebSocket) when a new server is created.

- **Sidebar** — the sidebar is split across several files: `Layout.tsx` (~100 lines) is the outer shell (mobile overlay, hamburger toggle, context-menu overlay, Outlet), `Sidebar.tsx` owns the `<aside>` element, the flat root-level group list, root-level ungrouped `ServerRow`s (siblings of the Groups — there are no virtual "All Servers"/"Ungrouped" nodes), dialog orchestration, logout, and theme toggle. Tree expansion and drag-target state live in `useTreeState` (`web/src/hooks/useTreeState.ts`), a pure reducer (`treeReducer`, exported for unit tests) over the `expanded`/`seeded`/`dragOverId` state: newly appearing Groups auto-expand while Groups the user collapsed never re-expand (the seed-new-groups invariant is a reducer transition, not a component effect — the hook re-dispatches `groups_updated` with the current Group ids whenever `groupList` changes, initial load included, and the reducer no-ops when nothing is fresh), and `dragOverId` uses the exported `ROOT_DROP` sentinel for blank-space drops. `parseDrop` (same module) resolves the `application/json` drag payload — only `{type:"server", id}` payloads move anything; DOM drag events are translated to primitives at the component, so nothing DOM-shaped crosses the seam. The whole tree area is a drop target: dropping a Server on blank space moves it out of its Group (Group and Server rows stop propagation so they remain their own targets). `GroupRow.tsx` renders a single root-level group row — including the hover delete quick-action and the expandable member-server list — plus the exported `ServerRow` link (status dot, drag handle, active-state highlight), `GroupNameDialog.tsx` is the shared create/rename dialog with inline validation (Save disabled while the name is empty, `409 duplicate_name` shown as an inline error), `MoveToDialog.tsx` is the move-to dialog (select a target Group or "no group", pre-selected from the Server's current Group; `onSubmit` receives the chosen Group id), `DeleteGroupDialog.tsx` is the delete-confirm dialog mirroring the server-delete flow (destructive confirm button; the message states that the group's servers become ungrouped), and `useSidebarActions.ts` wraps `useGroups` + `useMonitorState` to provide CRUD callbacks (create/rename/delete group, move server) that orchestrate API calls, dispatch, refetch, and success toasts — the create/rename/delete callbacks throw on API failure so callers can render inline validation or error toasts. Groups are flat (no nesting); Servers are moved into a Group via drag-and-drop or the "Move to..." dialog, and dropped on blank tree space to leave their Group. The shared `ContextMenuOverlay` component is rendered in `Layout` (not `Sidebar`) because the sidebar `<aside>` uses CSS `transform` for the mobile slide animation, which creates a new containing block that breaks `position: fixed`.

- **Dashboard server card context menu** — right-clicking a Server card on the Dashboard opens an in-app context menu with the same Edit / Delete / Console actions available on the Server detail page. Edit fetches the full Server over the API before opening the edit dialog, Delete opens the delete-confirm dialog and dispatches `remove_server`, and Console opens the console page in a new browser tab. The menu reuses the shared `ContextMenuOverlay` component with Dashboard-local menu state (safe because the Dashboard content area has no CSS `transform`), and blank dashboard space keeps the browser's native context menu.

- **i18n** — i18next initialized at module import time (not lazy). `getAppLang()` reads the server-injected `<meta name="app-lang">` tag at init via `document.querySelector`. Tests running under jsdom must ensure the DOM is available before the `i18n` module is imported; `setup.ts` imports `../i18n` early, so jsdom must be initialized by then. The language meta tag is injected by the Go server into `index.html` on first load and during setup.

- **Dashboard disk card** — `ServerCard` shows only the root partition (`mountPoint === "/"`) via `getRootPartition()`, not the highest-usage partition. The label uses the i18n key `serverCard.disk` (not the mount point). Full per-partition detail lives on the ServerDetail page.

- **Test data factories** — `makeMetrics(overrides)` uses per-field nullish coalescing (`overrides.X ?? sensibleDefault`) so partial overrides don't lose sibling defaults. Some test files still use the older top-level spread pattern (`{...defaults, ...overrides}`) which drops unmentioned keys — prefer the per-field pattern for new code. `makeProcess` factories consistently use the per-field pattern.

- **Processes tab** — `ProcessesTab` component uses `useProcesses` hook (useReducer + useEffect) which auto-polls `GET /api/servers/{id}/processes` every 3s. The hook structure mirrors `useCrons` (useReducer + Action discriminated union, exported reducer for testability), but adds 3s auto-polling via `setInterval` which `useCrons` does not have. Process data is not in the WebSocket snapshot; it is fetched independently when the user switches to the Processes tab. The table is a flat sortable list (not a tree). Command column shows only the executable name; full command and PPID are available on hover via `title`. Column widths are user-resizable via drag handles on header cells. The manual refresh button is at the far right and only visible when auto-refresh is toggled off. Kill button is a red `XCircle` icon with a SIGTERM/SIGKILL confirmation dialog.
